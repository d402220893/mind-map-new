## 1. 目标与背景

- 观测结论（详见《启动慢分析报告_2026-10-15》）：启动 ~8s 中 **~82% 耗在 Edit 路由懒加载 chunk（715.js，3.65MB）的下载+解析+执行**；静态首屏 ~1.0s；画布构造+多文件加载 <0.1s；主进程 boot 0.28s。
- 真痛点是双重的：总时长 8s + **1.2s→8.0s 的零信息盲窗**（§10 P-UX 单独处理体感）。

## 3. 启动关键路径模型

```
主进程 boot (0.28s) ──→ loadFile
    ├─ ① 静态首屏：chunk-vendors(1.48MB)+app.js(0.15MB) 下载+解析+执行 (~1.0s) 【必需】
    ├─ ② Edit 路由懒加载 chunk 715.js (3.65MB) 下载+解析+执行 (~6.5s) 【大部分可延迟】
    └─ ③ Vue 挂载 + MindMap 构造 + 三文件加载 (<0.1s) 【必需】
体感层（正交）：#boot-loading 闪屏 77ms 即现 → 1.2s 后零信息盲窗 → 8.0s 突然完成
```

**成分分类与延迟触发条件**：

| ②中成分 | 体积贡献 | 分类 | 延迟触发条件 |
|---------|---------|------|-------------|
| katex+quill（Formula 插件连带） | ~460KB | 可延迟 | 打开含公式数据 / 用户首次插入公式 |
| pdf-lib（ExportPDF）+ jszip（ExportXMind） | ~350KB | 可延迟 | 用户首次执行对应导出动作 |
| 内嵌 base64 PNG（79 处） | ~550KB | 可外置（P1-3） | 按需读取 |
| toast-ui Editor/Viewer 捆绑（md/备注栈） | ~600KB+ | 可延迟（P1-1 组件级） | 首次打开 md 编辑/备注 |
| simple-mind-map 核心+其余插件 | ~1.6MB | **必需**（画布本体） | — |

**模型推论（方案合法性来源）**：②占 82%，其中「可延迟」成分体积 ~1.6MB+——把可延迟成分从 ② 摘出是唯一架构级杠杆；①③合计 ~1.1s 是地板。**理论下限 = 主进程 boot 0.28s + ① ~1.0s + ③ ~0.1s ≈ 1.4s**，M3 的想象空间由此封顶。

## 4. 依赖 DAG 与降级路径

### 4.1 依赖 DAG

```
P0(度量基建) ──┬─→ P1-1(备注异步化) ─→ P1-3(PNG外置) ─→ P2(preload) ─→ P-UX-a ─→ M1
               └─→ P1-2(插件延迟注册+回灌) ──────────────────────────────→ M2
P3(归因) ←─ 「bundle 终态已知」
P-UX-a ←─ P0（timeline 变量来自 §6.0-3 聚合）
```

三条硬依赖及理由：

1. **P1-2 / P2 / P-UX-a ← P0**：没有统一 edit_ready 口径与 20 轮协议，一切"达标/回退"判定无标尺。
2. **P3 ← 「bundle 终态已知」而非「M2 成功」**：归因必须在不再变化的 bundle 上做。M2 落地后终态=瘦身包；M2 三批全败恢复全静态后终态=原包——两者都是确定状态，归因均有效。E3（组件树探针）例外：其结论只在「插件已拆出」的 bundle 上有意义，M2 全败时 E3 顺延至 bundle 下次确定变更（与 §4.2 互引）。
3. **P-UX-a ← P0**：三段式时间轴变量来自 §6.0-3 聚合脚本，无数据即无发布（§10.2）。

### 4.2 降级路径（含目标重排）

| 情形 | 动作 | 目标重排 |
|------|------|---------|
| M1 中位 >6.0s（新口径校准后阈值，下同） | 按 §6.1 回退判定定位劣化项，逐项 revert；达标项保留 | **M1 目标顺延为 ≤6.5s** 并与基线报告核对差距 |
| M2 单批次异常 | 该批次退回静态组，audit 断言同步收窄，其余批次继续 | ≤5.0s（按退回批次体积折减重排） |
| M2 三批全部失败 | `alwaysRegisterAllPlugins=true` 恢复全静态（现状等价），audit 断言回退到 M1 规则 | 放弃 M2；P3 归因**仅执行 E1/E2**（不依赖插件拆出），**E3 顺延**至 bundle 下次确定变更；M3 预期收益同步下调 |
| M3 归因后无对应手段 | 冻结 M3 | 转 Defender 排除项推动 + Electron 升级评估专项 |
| 任一步回退判定触发 | §6.1 硬阈值（中位劣化 >5% 或 p90 >10%） | 不带病合并，定位后重跑 |

**顺延语义（v1.2.2 定死）**：「顺延」一律指**目标值不变、达成时间顺延**，不做同比例放宽——放宽阈值会让"达标"失去跨里程碑可比性。若顺延后判定 M1→M2 的降幅要求超出剩余优化项的收益能力上限（各步实测收益累加 < 差距），不放宽阈值，改走本表「M2 批次异常」行的重排降级，并在 §16 附录记录重排依据。

## 5. P1-1：备注/md 组件异步化

**靶点**：`NodeNote`（`Edit.vue:116,179` 静态）与两个 toast-ui Viewer（`Toolbar.vue:157` 静态）改 `defineAsyncComponent`（`MdEditor` 已是异步组件，`Index.vue:85` 同款写法参照）。

### 5.2 策略定死：首次延迟 + 常驻

- 首次触发（打开备注/md 编辑）才开始加载对应 chunk；加载完成后**组件常驻不卸载**，后续显隐走既有 v-show 通道。
- **明令禁止**：v-if 包裹异步组件（状态丢失）；keep-alive 叠加补救（多余状态层，与常驻语义冲突）。两条均为纪律条。

### 5.3 空闲预热（首次延迟的优化器，非替代者）

- `edit_ready` 后 `requestIdleCallback` 预 resolve 异步组件的 loader。
- 预热只改变首次加载的**时机**，不改变加载的**形态**——启动关键路径不加载、组件常驻两条铁律不变（与 §5.2 一致性见 §7.3 三态表）。

## 6. P0 度量基建 + P1-2 插件延迟注册

### 6.0 P0 基建

1. 渲染端 `perfMark` 统一经 IPC `smm:startup-perf` 落盘主进程（prod 下 console.log 被 terser 摘除的教训）；主进程 `bootMark` 已在场（main.js:116-121）。协议扩展：`{name, ts, extra}` → 主进程写 `perf <name> <delta> [extra]`；无 name 保持旧 `edit_ready` 行为（向后兼容）。
2. **edit_ready 语义修正**：旧口径（`Edit.vue:1865` 首帧近似）保留；新口径 `edit_ready_loaded` 由 initLoadGuard 终态（loaded/failed/看门狗强制）发出。两线并行，聚合脚本以 `edit_ready_loaded` 为主指标。
3. 聚合脚本：读 `startup_main_*.log` + perf 落盘 → 统计（hot 中位/p90、cold 单列、failed 单列）→ 产出 `boot-timeline.json`（§10.2 消费）。

### 6.1 度量协议规格（写死）

**edit_ready 定义（唯一口径）**：

- 语义 = **三个文件全部加载完成**（用户既定启动完成标准）= 全部待载工作簿达终态：激活 workbook 由 initLoadGuard 置 `loaded`（根非空 + 三文件就绪），非激活 workbook 以 `loadSheetData` 返回为准；多 workbook 场景以**最后一个**终态为准。启动场景实际退化为激活簿终态（非激活簿懒加载属窗口外，见 §8.5）。
- 时刻口径 = 渲染端在上述终态时发标记、**主进程写盘时刻**（IPC 排队 <1ms 恒定）。**首帧时刻彻底退出 edit_ready 定义**（`first_render_done` 降为独立归因埋点，不留"待核对"）。
- 基线可比性：旧口径基线 7997ms 标注历史参考（§16 两行分列）；P0 落地后第一个动作 = 重测 20 轮建新口径基线，此后一切对比用新口径。

**样本与统计口径**：

- 每步出包后 20 轮（启动→30s→taskkill→下一轮，复用丢文件回归流程）。
- 主指标 = **hot 中位**；辅指标 = hot p90；另记 min/max 供归因。
- **冷热判定**：部署 app.asar 后第 1 轮记 cold，第 2-20 轮记 hot。hot 口径消除 Defender 首扫/OS 缓存方差；cold 单列只作尖峰观测，不参与通过判定。
- **failed 轮处理（v1.2.2 定死）**：任一工作簿达 failed → 该轮**单列统计**：不计入中位、**不计入 p90**（failed 耗时含 20s 看门狗等待，混入会拉爆 p90，使达标被误判不通过），只报「failed 轮数」。**连续 ≥2 轮 failed = 硬失败**，不等阈值判定直接触发 §4.2 回退流程；单轮 failed = 该步重跑一次（≤1 次重试），重跑仍 failed 按硬失败处理。

**通过/回退判定（硬阈值）**：

- M1 通过：hot 中位 ≤6000ms（校准后）**且** hot p90 ≤7500ms。
- M2 通过：hot 中位 ≤4500ms（校准后）**且** hot p90 ≤6000ms。
- 任一步**回退判定**：hot 中位劣化 >5%，或 hot p90 劣化 >10% —— 触发定位/回退，不带病合并。
- 单步优化项（非里程碑级）通过：较上一步 hot 中位下降 ≥ 其预期收益的 50%（如 P2 预期 -0.3s → 实测 ≥150ms），否则按 §4.2 降级处理。

### 6.2 插件延迟注册的实例级真相（定死）

### 6.3 回灌预注册（正确性关键）

- **挂接点 = `loadSheetData` 唯一漏斗**（启动恢复/openPath/切 sheet/新建全收敛于此，无旁路）。
- **扫描 = 表驱动 `scanPluginMarks(root)`**：遍历节点树 `nodeData.data`，按 §6.2 表的 marks 字段判定（`data.formula` → Formula 插件，Formula.js:114；`data.richText` → RichText，RichText.js:97）。新插件注册时在表里追加 marks 即可，扫描逻辑零改动。
- **并行 `Promise.all`** 加载全部命中插件后统一 addPlugin；失败策略：任一插件动态 import 失败 → 记 `Result{ok:false,error}`，该插件缺失降级（公式显示原文），不阻塞其余插件与加载流程，同时上报遥测。
- **预注册 Promise resolve 是 initLoadGuard 置 `loaded` 的硬前置**——闸门 A 不得在插件就绪前放行，防止用户在 katex 未就绪时编辑公式节点。Promise 挂在 guard 状态对象上，20s 看门狗同样覆盖预注册阶段。

## 7. 首次延迟与预热语义

### 7.1 两条铁律（不变）

启动关键路径不加载可延迟成分；异步组件加载后常驻不卸载。

### 7.2 语义关系

预热是「首次延迟」的**优化器而非替代者**：预热成功 = 首次打开时已在缓存（延迟成本归零，但"首次延迟+常驻"的架构形态未变）；预热失败/未及预热 = 首次延迟按原样生效。两种策略不是二选一，是同一机制的两个时点。

### 7.3 三态行为表

| 状态 | 用户首次触发时行为 |
|------|------------------|
| 预热已 resolve | 直接显示（零等待） |
| 预热 in-flight | await 同一个 Promise（defineAsyncComponent 天然单例，无重复请求） |
| 未预热/失败 | 触发首次加载，loading 态 + 常驻 |

### 8.1 audit_bundle.mjs 构建期断言（随里程碑升级）

- P2 上线追加：index.html 含 715 chunk 的 preload hint（仅 smoke，性能验收见 §9）。
- **兼作 timeline 闸门**：发布构建检查 `dist/boot-timeline.css` 在场，缺失即失败（§10.2）。可挂进 build_now.sh 测试硬闸门段。

### 8.2 多 workbook 轮换注册专项

A/B 两 workbook 分别打开含公式文件，各自可编辑可渲染；关闭 A 后 B 的插件状态不受影响（v1 只注册不卸载 ⇒ 天然满足，但需测试坐实）。

### 8.3 回灌专项

v2.0.36 事故文件（裸根 .smm）、含公式+富文本+水印历史文件、外部工具产 .smm 各一发；断言：公式渲染非原文、`loaded` 前闸门不放行。

### 8.4 兜底开关

兜底开关 `alwaysRegisterAllPlugins`（localConfig，默认 false）。

### 8.5 与 v5 stall 探测器的关系（启动窗口边界定义）

- **启动窗口 = 从本次启动首次 `loadSheetData` 开始，至全部待载工作簿达 `loaded`/`failed` 终态为止——以状态界定，不以时间界定**（启动后 5s 用户即编辑但窗口未闭合，仍在启动窗口内）。
- **待载工作簿集合 = 启动恢复流程启动那一刻枚举的 workbook 列表**（localStorage 恢复 + 启动参数文件）。**不含启动后用户新开的 workbook**——后者走常规 `loadSheetData` 流程，自带 guard 生命周期，属窗口外。
- 窗口内：启动期看门狗（固定 20s）唯一可写 `loadPhase=failed`；窗口外：v5 运行期 stall 探测器（自适应阈值、永久只读 loadPhase、只报慢发遥测）。交接点 = 窗口闭合这一次瞬时状态迁移，**无重叠**。本条即 v5 的接口契约。
- **运行期加载超时出口（v1.2.3 显式登记，注意 8）**：启动后新开/切换的 workbook 若加载卡住，启动看门狗不覆盖（窗口外）、stall 探测器不写 failed（v5 设计）——此口子**登记为 v5 的待办**：v5 常规加载流程须自带「运行期加载超时→failed」出口（如 loadSheetData 挂 20s 超时守卫），否则 loading 永久悬挂用户只见转圈。**不在本方案实施范围**，但 P1-2 的预注册 Promise 同样需要该出口覆盖（实施时 loadSheetData 级超时一并接入，见 §6.3）。已升 R8。

## 10. P-UX：加载进度反馈

### 10.1 物理约束（不变）

主线程被 715.js 占满 → 页面 JS 无法更新进度；CSS 动画走合成器线程不受阻塞影响（first-paint 77ms 即证）；主进程侧 `session.webRequest.onCompleted` 可观测各 chunk 下载完成。

### 10.2 UX-a：CSS 三段式进度——时间轴**绑定优化目标，构建期生成**

- `#boot-loading` 三段进度（`载入框架`/`载入编辑器`/`初始化画布`），**动画时长全部引用 CSS 变量** `--boot-t1/--boot-t2/--boot-t3`，**禁止在代码里硬编码 1.2/6.5/8.0**。
- 变量来源：§6.0-3 聚合脚本产出 `boot-timeline.json`（t1=①静态首屏 hot p50、t2=②chunk 完成窗口 hot p50、t3=edit_ready hot p50）→ **build_now.sh 部署阶段生成 `dist/boot-timeline.css`** → index.html 引用。
- **timeline 是发布构建的必备产物，失败语义**：发布构建时 timeline 文件**缺失或生成失败**（聚合脚本报错 / hot 样本不足 20 轮 / json 字段缺失）→ **构建硬失败**（AUDIT_BUNDLE 闸门项，exit≠0 并输出具体缺失原因），**不允许降级发布**——发布包里不存在回退态。
- **回退仅存在于 dev 构建**（不出发布物），且回退形态为**不确定态脉冲动画**（indeterminate，不承诺任何进度）——任何定长数字都有失配方向，只有不确定态无承诺即无失配。
- 生命周期：**每个里程碑出包自动重生成时间轴**，M1/M2 优化落地后三段自动收紧，永不与实测脱节。
- 消失仍由 `edit_ready` 渲染端移除；段内推进为时间近似，段边界对齐实测分位。

### 10.3 UX-b（备选）：主进程真里程碑 splash

独立 frameless 窗口由主进程驱动（`webRequest` 里程碑 + `smm:renderer-ready` 终点经 `splashWin.webContents.send` 推真进度）。仅当 UX-a 上线后仍被诟病再实施。

## 11. P3：归因实验 + 条件优化

### 11.1 定死事实

- Electron v25.7.0 CustomScheme privileges 无 `codeCache`（已查证官方 custom-scheme.md）→ app:// codeCache 路线撤下，登记「升级 Electron ≥28 后重评」。
- parse "2-4s" 作废（3.65MB ≈ 365ms 全量 parse，上浮 0.4-1s），6.5s 构成未归因。

### 11.2 归因实验（零产品代码改动，依赖「bundle 终态已知」后执行，见 §4.1-2）

| 实验 | 手段 | 判读 |
|------|------|------|
| E1 V8 采样 | `--js-flags=--prof` + `--prof-process` 离线聚合 | parse/compile/execute 占比 |
| E2 IO 归因 | 同包冷/热 OS 缓存 A/B + 排除目录 A/B | asar IO + Defender 占比 |
| E3 组件树成本 | 探针包（Edit.vue 换空组件，仅实验不入发布） | 组件树+插件求值成本（M2 全败时顺延） |

结论分支：execute 主导 → 收益已被 M2 覆盖，M3 降级为 Electron 升级评估；IO/Defender 主导 → 排除项+读取优化；parse 意外主导（<10%）→ 重提 bytecode 预编译。**M3 时间目标归因后另立（TBD）。**

## 12. P4：element-plus 按需导入（机会项——排序依据）

判断依据 = ROI 三元组：

1. **收益**：~0.3-0.5s，< 基线 5%；且 vendors 仅占 ①（~1.0s）的一部分，M1 后 ① 在总耗时中占比进一步降低，P4 收益占比不升反降。
2. **改动面/风险**：全局组件注册方式变化（局部注册替代全局）、`ElMessage` 等函数式组件样式需手动 import——长尾回归风险遍布全站 UI，而其他优化项全部是局部改动。
3. **机会成本**：同样的工时投在 P1-2 批次，收益是它的 2-3 倍。

结论：收益低 × 风险面广 × 机会成本高 → 末位机会项。**触发重评条件**：M1/M2 落地后若 ① 在剩余耗时中占比 >40%，P4 升格为 M3 候选手段。
