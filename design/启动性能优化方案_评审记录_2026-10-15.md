## 三、报告：不符合"好架构文档"的地方

### 1. 它是"观测报告"，不是"架构分析"

报告回答了"哪里慢、多慢、为什么慢"，但没回答：

- **这个启动流程本身的设计是否合理？**（比如"Edit 页是否必须启动时加载"）

观测报告不需要回答这些，但**如果把它当"架构输入"用，就缺了一层**。

### 2. 缺"用户感知"的分解

报告说"用户感知 7-8s 是转圈等待"，但没有把**用户感知**和**技术耗时**对齐：

- 0-77ms：白屏（几乎无感）
- 77ms-1.2s：闪屏"加载中…"（可接受）
- 1.2s-8.0s：**闪屏还在，无任何反馈更新**（开始怀疑卡死）
- 8.0s-8.1s：画布出现

**真正的体验问题是"1.2s-8s 无反馈"**，报告没把这个说透。这一点方案 v1.1 的 P-UX 补上了。

### 3. §七的"100 次开闭测试"措辞不严谨

### 4. md markDirty 被列为"次要发现"，但它是 v5 的直接证据

`内存测试.md` 的 `markDirty` 载入即置位 → 退出时回写相同内容。这不是"次要"，是**会被 v5 的"覆盖前先备份"放大**的问题（每次退出产生 .bak）。方案 v1.1 已经把它划到 v5 范围（§2.2），**但报告本身没升级它的严重性**。

## 五、方案 v1.1：不符合"好架构文档"的地方

### 1. 它是"施工方案"，不是"架构设计"

优点里说的"定死 5 项"，都是**施工细节的定死**，不是**架构层面的决策**。方案仍然没有：

- **启动关键路径模型**：哪些是启动必需、哪些可延迟、延迟触发条件——没有一张图说清
- **依赖 DAG**：P0→P1-1→P1-2 的依赖是文字描述，不是显式建模
- **降级路径**：M1 不达标怎么办、M2 灰度失败怎么办、M3 归因后无手段怎么办——只有"回滚"，没有"降级后目标如何重排"

### 2. P0 的"度量协议"仍然没定义规格

§4 说"perf 经 IPC 落盘 + audit_bundle.mjs"，但：

- `edit_ready` 的定义是什么？（主进程收到 IPC 的时刻？渲染端发出的时刻？）
- 采集频率、样本量、统计口径（中位/p90/冷热分离）？
- 怎么判定"这次是冷缓存还是热缓存"？

§11.1 给了"每步出包后跑 20 轮"的流程，但**没给"什么算通过"的统计判定**。

### 3. P-UX 的"三段式"时间是硬编码的

§7.2："时间轴对齐当前实测分位（1.2s / 6.5s / 8.0s）"——**这三个数字是当前基线**。如果 M1/M2 优化后变成 0.8s / 3s / 4.5s，三段式的时间轴就对不上了。方案没说"这三段怎么随优化同步更新"。

### 4. §6.3 的"20s 看门狗覆盖预注册阶段"——看门狗和 v5 的 stall 探测器是什么关系？

§6.3："Promise 挂在 guard 状态对象上，20s 看门狗同样覆盖预注册阶段"。但 v5 覆盖防护方案里有个"stall 探测器"（自适应阈值、只报慢不翻 failed）。**这两个是同一个东西吗？** 20s 是固定阈值，v5 是自适应。方案没说清。

### 5. §5.3 的"空闲预热"和"首次延迟"的一致性

§5.2 定死"首次延迟 + 常驻"，§5.3 又加"edit_ready 后 requestIdleCallback 预 resolve"。那**首次打开备注时，chunk 已经预 resolve 了，还算"首次延迟"吗？** 两种策略的交互没写清——预 resolve 成功后，"首次延迟"实际上不存在了；预 resolve 失败后，"首次延迟"才生效。

### 6. §10 的 P4 被列为"机会项，末位"，但没有优先级排序依据

为什么 element-plus 按需是"机会项"而不是 M1？因为"收益 0.3-0.5s 但改动面大"？方案只给了收益，没给"为什么排在最后"的判断依据。

## 二、仍需注意的地方（不是硬伤，是实施时要知道）

### 注意 1：§6.1 "新口径 ≥ 旧口径"的预期偏差，没有量级

§6.1 说：

> 预期偏差方向：新口径 ≥ 旧口径（多 workbook 时多算一次 loadSheetData），单 workbook 场景两者接近。

**方向说了，量级没说。** 如果新口径比旧口径大 500ms，那 M1 目标 ≤6000ms 是"新口径 6000"还是"旧口径 6000"？v1.2.1 说"此后 M1/M2 对比一律用新口径"，但 §2.1 的目标表**没标口径**。

**建议**：§2.1 目标表加一列或脚注——"目标值均为新口径（loaded 终态）"。否则实施时看到 6000ms，会有人按旧口径理解，产生"到底达没达标"的争议。

### 注意 2：§8.5 "启动窗口"的定义里，"全部待载工作簿"的枚举时机没写

§8.5：

> 启动窗口 = 从本次启动首次 loadSheetData 开始，至**全部待载工作簿** initLoadGuard 达终态为止

问题：**"全部待载工作簿"是什么时候确定的？**

- 启动时恢复上次会话的 N 个 workbook——N 在"首次 loadSheetData 开始"时已知，OK。
- 如果启动后用户**又打开了一个新文件**（新 workbook）——这个新 workbook 算不算"待载"？如果算，窗口永远关不上（用户随时开新文件）；如果不算，那"全部待载"就是"启动瞬间的 N 个"。

**建议**：§8.5 明确"待载工作簿 = 启动恢复流程启动时枚举的那批，不含启动后用户新开的"。否则窗口边界会有歧义。

### 注意 3：§6.1 的"任一工作簿达 failed 则以 failed 事件为准（该轮记为异常，不入通过统计但计入 p90 样本）"——**p90 样本里混入 failed 轮，p90 含义会偏**

§6.1：

> 任一工作簿达 failed 则以 failed 事件为准（该轮记为异常，不入通过统计但计入 p90 样本）

问题：

- "不入通过统计"意味着**不参与中位数计算**，OK。
- "但计入 p90 样本"意味着**failed 轮会被算进 p90**。failed 的耗时可能异常长（看门狗 20s 才判 failed），会**把 p90 拉高**。
- 结果：M1 通过条件是"hot 中位 ≤6000 且 hot p90 ≤7500"，如果某轮 failed 耗 20s，p90 会被拉爆，**明明优化达标却被判不通过**。

**建议**：§6.1 明确 p90 也排除 failed 轮，或 failed 轮**单列统计**（不计入 p50/p90，只报"本轮 failed 数"）。否则 p90 会被异常轮污染。

### 注意 4：§4.2 的"M1 目标顺延为 ≤6.5s"——**顺延后，M2 的 ≤4.5s 还算数吗？**

§4.2：

> M1 中位 >6.0s → ……M1 目标顺延为 ≤6.5s 并与基线报告核对差距；M2 相应顺延；P4 不变

问题：

- "M2 相应顺延"——是"M2 目标不变（≤4.5s），只是时间上晚一点达成"，还是"M2 目标也顺延（比如 ≤5.0s）"？
- 如果 M2 目标不变但 M1 基线变高，那 M1→M2 的**降幅要求变大**了（从 6.0→4.5 变成 6.5→4.5），可能超出 P1-2 的收益能力。

**建议**：§4.2 明确"M2 顺延"是"目标值不变、达成时间顺延"还是"目标值同比例放宽"。二选一说清。

### 注意 5：§10.2 的 timeline 文件"发布构建必备"，但**构建失败时怎么办**没写

§10.2：

> timeline 文件定为发布构建必备产物 + dev 回退改不确定态脉冲

问题：

- 发布构建时，如果 `boot-timeline.json` 生成失败（聚合脚本报错、数据缺失），构建是**失败**还是**降级为 dev 的不确定态脉冲**？

- 如果是降级——那"必备"就不成立，发布版也可能出现不确定态脉冲，跟 dev 一样。

**建议**：§10.2 明确"发布构建时 timeline 生成失败 → 构建失败（硬闸门）"，还是"降级 + 告警"。二选一说清。

### 注意 6：文件头部"⚠️ 恢复记录"——**评审记录和方案本体分离是对的，但"勿再粘入本文件"的约束靠什么保证？**

## 10. P-UX：加载进度反馈

### 10.1 物理约束（不变）

主线程被 715.js 占满 → 页面 JS 无法更新进度；CSS 动画走合成器线程不受阻塞影响（first-paint 77ms 即证）；主进程侧 `session.webRequest.onCompleted` 可观测各 chunk 下载完成。

### 10.2 UX-a：CSS 三段式进度——时间轴**绑定优化目标，构建期生成**

- `#boot-loading` 三段进度（`载入框架`/`载入编辑器`/`初始化画布`），**动画时长全部引用 CSS 变量** `--boot-t1/--boot-t2/--boot-t3`，**禁止在代码里硬编码 1.2/6.5/8.0**。
- 变量来源：§6.0-3 聚合脚本产出 `boot-timeline.json`（t1=①静态首屏 hot p50、t2=②chunk 完成窗口 hot p50、t3=edit_ready hot p50）→ **build_now.sh 部署阶段生成 `dist/boot-timeline.css`** → index.html 引用。
- **timeline 是发布构建的必备产物，失败语义（v1.2.2 定死，注意 5）**：发布构建时 timeline 文件**缺失或生成失败**（聚合脚本报错 / hot 样本不足 20 轮 / json 字段缺失）→ **构建硬失败**（AUDIT_BUNDLE 闸门项，exit≠0 并输出具体缺失原因），**不允许降级发布**——发布包里不存在回退态。
- **回退仅存在于 dev 构建**（不出发布物），且回退形态为**不确定态脉冲动画**（indeterminate，不承诺任何进度）——任何定长数字都有失配方向，只有不确定态无承诺即无失配。
- 生命周期：**每个里程碑出包自动重生成时间轴**，M1/M2 优化落地后三段自动收紧，永不与实测脱节。
- 消失仍由 `edit_ready` 渲染端移除；段内推进为时间近似，段边界对齐实测分位。

独立 frameless 窗口由主进程驱动（`webRequest` 里程碑 + `smm:renderer-ready` 终点经 `splashWin.webContents.send` 推真进度）。仅当 UX-a 上线后仍被诟病再实施。

## 11. P3：归因实验 + 条件优化

### 11.1 定死事实

### 11.2 归因实验（零产品代码改动，依赖「bundle 终态已知」后执行，见 §4.1-2）

| 实验       | 手段                                          | 判读                       |
| -------- | ------------------------------------------- | ------------------------ |

## 12. P4：element-plus 按需导入（机会项——排序依据）

判断依据 = ROI 三元组：

1. **收益**：~0.3-0.5s，< 基线 5%；且 vendors 仅占 ①（~1.0s）的一部分，M1 后 ① 在总耗时中占比进一步降低，P4 收益占比不升反降。
2. **改动面/风险**：全局组件注册方式变化（局部注册替代全局）、`ElMessage` 等函数式组件样式需手动 import——长尾回归风险遍布全站 UI，而其他优化项全部是局部改动。
3. **机会成本**：同样的工时投在 P1-2 批次，收益是它的 2-3 倍。

结论：收益低 × 风险面广 × 机会成本高 → 末位机会项。**触发重评条件**：M1/M2 落地后若 ① 在剩余耗时中占比 >40%，P4 升格为 M3 候选手段。
